# Building for the browser

This page walks through setting up `wasm32-unknown-unknown` and
building `tpt-nrg-wasm` for browser / edge consumption.

> **Note:** this requires the `wasm32-unknown-unknown` target, which
> must be installed on the build machine via `rustup`. CI workflows
> that build for the web run inside a container that has the target
> pre-installed.

## One-time setup

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
```

## Build

`tools/build-npm-package.sh` is the supported way to produce the package: it
runs `wasm-pack`, layers the hand-written `crates/core/tpt-nrg-wasm/npm/`
metadata (name, licence, repository, `files`) over the generated output, copies
the repository licences in, and refreshes the checked-in TypeScript
declarations.

```sh
tools/build-npm-package.sh            # build into dist/npm, refresh npm/*.d.ts
tools/build-npm-package.sh --check    # fail if the checked-in .d.ts is stale
tools/build-npm-package.sh --no-opt   # skip the wasm-opt pass
```

To run `wasm-pack` by hand, note the argument order: **wasm-pack's own flags
come before the crate path**, and anything after the path is forwarded verbatim
to `cargo build`, which is how `--features wasm` reaches cargo. Getting this
wrong produces a confusing `cargo build` usage error.

```bash
wasm-pack build \
    --target web \
    --release \
    --out-dir pkg \
    --out-name tpt_nrg_wasm \
    crates/core/tpt-nrg-wasm \
    --features wasm
```

The crate declares `crate-type = ["cdylib", "rlib"]`, which is what
`wasm-pack` needs; the `rlib` half keeps the crate usable and testable from the
rest of the workspace in native builds.

The output lands in `pkg/`:

- `pkg/tpt_nrg_wasm_bg.wasm` — the compiled WASM module
- `pkg/tpt_nrg_wasm.js` — JS glue generated by wasm-bindgen
- `pkg/tpt_nrg_wasm.d.ts` — TypeScript type declarations
- `pkg/package.json` — replaced by the one in `crates/core/tpt-nrg-wasm/npm/`

## Consume in a JavaScript project

```bash
npm install ./pkg
```

```js
import init, { wasm_run_powerflow_json, WasmMicrogridController } from "tpt-nrg-wasm";

await init(); // load the .wasm file
const ieee14 = await fetch("/ieee14.json").then(r => r.text());
const result = wasm_run_powerflow_json(ieee14);
console.log("converged:", result.converged, "losses:", result.losses_mw, "MW");

const ctrl = new WasmMicrogridController('{"assets":[],"grid_connected":true}');
const actions = ctrl.step("{}");
console.log("control actions:", actions);
```

## Bundler integration

For a `vite` / `trunk` / `webpack` setup, import the package and the bundler
will inline the WASM module.

The [playground](playground.md) is a complete, dependency-free browser app for
this crate: pick a case, solve it, and draw the diagram, with no build step
beyond producing `pkg/`. It is deployed to GitHub Pages by
`.github/workflows/playground.yml`, and `playground/tests/smoke.mjs` exercises
the same module from Node so CI needs no browser.

## Edge / bare-metal

For embedded targets (`wasm32-unknown-unknown` with `+no_std`),
restrict the dependency tree further:

```bash
wasm-pack build \
    --target bare \
    --release \
    crates/core/tpt-nrg-wasm \
    --features wasm
```

This strips the JS glue and produces a freestanding `.wasm` suitable
for use inside a microkernel hypervisor.
